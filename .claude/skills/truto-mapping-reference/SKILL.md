# Truto mapping & proxy config — verified reference

Ground truth for how Truto's proxy config and unified mappings behave **at runtime**.
Every claim below cites `file:line` in the `truto` backend.

**If a prompt template, a doc, a memory, or a plausible-sounding assumption contradicts
this file, this file wins.** If something here looks wrong, re-read the cited file before
acting — do not split the difference.

The three things that cause the most wrong output, in order:

1. Assuming config lives in checked-in files. It does not — see §1.
2. Guessing which JSONata bindings exist in a given mapping field. They differ per field — see §4.
3. Writing `response[].{...}` for a list mapping. Wrong by default — see §5.

---

## 1. Where the config actually lives

There is **no checked-in source of truth**. Everything is rows in D1, authored through the
dashboard, the CLI, or the API.

| Layer | Table / column | Read it with |
|---|---|---|
| Proxy transport | `integration.config` | `truto integration list --name <slug>` then `truto integration get <id>` |
| Unified schema | `unified_model.resources.<resource>.schema` | `truto unified-model list` / `get <id>` |
| Base mapping | `unified_model_resource_method.config` | `truto unified-model-mapping list --integration-name <slug> --resource-name <r>` |
| Environment override | `environment_unified_model_resource_method.config` | `truto env-unified-model-mapping list --integration-name <slug>` |
| Account override | `integrated_account.unified_model_override[model][resource][method]` | `truto account get <id>` |

List filters are **named flags derived from `queryFields`**, not `-q key=value`
(`cli/src/resource.ts:269-274`). So: `--integration-name`, `--resource-name`,
`--method-name`, `--unified-model-id`.

### The local file mirrors are generated and gitignored

These paths are real, but they only exist **after you generate them**. On a fresh
checkout they are absent:

| Path | Generated by | Ignored at |
|---|---|---|
| `src/integration/integrationConfig/<integration>.json` | `yarn sync:integration` | `.gitignore:182` |
| `src/unified-model/mappings/<model>/<resource>/<integration>.yml` | `yarn export:unified-model-mappings` | `.gitignore:218` |

Both scripts need `TRUTO_BASE_URL` + `TRUTO_API_KEY` (and `TRUTO_REMOTE_*` to pull from
another environment) — `scripts/syncIntegrationsToLocal.js:120-125`,
`scripts/exportUnifiedModelMappingsToYaml.ts:14-19`.

`src/unified-model/models/<domain>.yml` **is** checked in and real — 26 domain files
(`accounting`, `ats`, `crm`, `hris`, `ticketing`, …). That is the unified contract.

> **If a mapping or integrationConfig directory is missing, it was never generated.**
> Say so and either run the sync script or read the platform through the CLI.
> Never infer a provider's config from its name, and never write a mapping against
> a proxy resource you have not actually read.

## 3. `mapping_version` and alias reuse — read this before writing any string

A string in a mapping field is sometimes an **expression** and sometimes a **pointer at
another method's mapping**. Which one depends on `mapping_version`
(`src/unified-api/fetchUnifiedApi.ts:67-180`, and the parallel getters at `:194-242`).

| `mapping_version` | A string in `response_mapping` / `query_mapping` / `request_body_mapping` / `path_mapping` / `error_mapping` / `request_header_mapping` / `response_header_mapping` |
|---|---|
| `2` | An **alias** only if it is exactly `list`, `get`, `create`, `update`, or `delete`. Anything else is a literal JSONata expression. |
| absent / `1` | **Always an alias.** An inline JSONata string is silently looked up as a method name and resolves to `undefined`. |

**Always set `mapping_version: 2` on anything you write.** Without it your inline JSONata
is dead config that returns nothing.

`query_schema` and `request_body_schema` behave differently: a string there is **always**
an alias, at any version (`fetchUnifiedApi.ts:181-194`). They are never JSONata.

`side_load.<path>.response_mapping` is a **method name**, not an expression
(`src/common/validateMappingJsonata.ts:12-16`, resolved at `fetchUnifiedApi.ts:1153-1160`).

So `response_mapping: list` on the `get` method means *"reuse the list method's response
mapping"* — the common, correct idiom when both return the same record shape.

## 4. JSONata bindings — differ per field, do not guess

Each mapping type is evaluated with its own context object. Referencing a binding that
is not in scope yields `undefined` silently.

| Mapping field | Bindings in scope | Source |
|---|---|---|
| `response_mapping` | `response`, `query`, `rawQuery`, `context`, `headers`, `body` | `mapResponseToUnifiedModel.ts:137-149, 229-236` |
| `query_mapping` | `query`, `body`, `context`, `before`, `id` — **no `rawQuery`** | `mapRequestQueryToUnifiedModel.ts:31-38` |
| `request_body_mapping` | `context`, `query`, `body`, `rawQuery`, `before`, `id` | `mapRequestBodyToUnifiedModel.ts:183-191` |
| `path_mapping` | `headers`, `body`, `query`, `rawQuery`, `context`, `before`, `id` | `mapRequestPathToUnifiedModel.ts:25-33` |
| `error_mapping` | `headers`, `error`, `body`, `query`, `rawQuery`, `context`, `before`, `id` | `mapResponseErrorToUnifiedModel.ts:31-40` |
| `request_header_mapping` | `headers`, `body`, `query`, `rawQuery`, `context`, `requestBody` | `mapRequestHeaderToUnifiedModel.ts:24-31` |
| `response_header_mapping` | `headers`, `body`, `query`, `rawQuery`, `context`, `response` | `mapResponseHeaderToUnifiedModel.ts:25-32` |
| `resource.expression` / `method.expression` | `query`, `rawQuery`, `body`, `context` | `getResourceOrMethod.ts:53-58` |
| `related_resources` (string form) | `data`, `query`, `rawQuery`, `before`, `id`, `context`, `body` | `fetchUnifiedApi.ts:320-329` |
| `before` / `after` step `run_if`, `state.expression`, `request.config` | `id`, `query`, `body`, `context`, `data`, `step` | `runSteps.ts:154-162, 184-190, 294-301` |

Notes that bite:

- **`query` vs `rawQuery`.** `query` is the parsed/normalised unified query; `rawQuery` is
  what the caller actually sent. `query_mapping` has no `rawQuery` at all.
- **`context`** in a `response_mapping` is the integrated account's context **plus**
  `before`, `id`, `integrated_account_id`, `documentParserApiUrl`, `documentParserApiKey`
  (`fetchUnifiedApi.ts:1190-1197`).
- **`remote_data` is added by the runtime**, not by you
  (`mapResponseToUnifiedModel.ts:175, 289-306`). Never map it yourself. It is stripped
  from the response unless the caller asks for it (`removeRemoteData.ts`).
- `before` step results are reachable as `before` in the main mapping, and as `step.<name>`
  *inside* the step list.

## 5. `response_mapping_method` defaults to `item` — `response.{...}`, not `response[].{...}`

`fetchUnifiedApi.ts:633-636`:

```ts
const responseMappingMethod =
  get(overrides, 'response_mapping_method') ||
  get(integrationMapping, [method, 'response_mapping_method']) ||
  'item'
```

And what `response` is bound to, per method (`fetchUnifiedApi.ts:1167-1175`):

| Unified method | `obj` handed to the mapper | With default `item`, `response` = |
|---|---|---|
| `list`, any **custom** method | the array of records | **one record**, expression run per record |
| `get`, `create`, `update`, `delete` | the single record | that record |

So **`response.{ ... }` is correct for every method, including `list`.** Write
`response[].{ ... }` only when you have explicitly set `response_mapping_method: array`,
which makes the expression run once against the whole array.

This contradicts a widely-copied prompt template. The template is wrong.

## 6. Schema vocabulary — `required` is a boolean on the property

`query_schema` and `request_body_schema` are `Record<fieldName, JSONSchemaObjectProperties>`.
The allowed keys on a property are exactly
(`src/common/schema/jsonSchemaObject.ts:35-51`):

`type` (`string|number|boolean|array|object|integer`), `$ref`, `description`,
`required` (**boolean**), `items`, `properties`, `mapping`, `default`, `format`, `enum`,
`additionalProperties`, `example`, `conditionallyRequiredDescription`, `xTrutoReference`.

- This is **not** standard JSON Schema. `required: ["a","b"]` at object level is wrong;
  it is `required: true` on each property.
- Unknown keys are rejected — it is an exact `object()`.
- `required: true` is enforced before the upstream call and returns the missing field
  names (`getMissingParameters.ts:12-24`).
- Use `conditionallyRequiredDescription` when a field is only required in some branch;
  it is surfaced to callers (`getParametersWithRequirementDescription.ts:10-19`).
- A field omitted from the schema is still passed through by a JSONata mapping — the
  schema governs validation and docs, not reachability.

## 7. The override ladder

Three rungs, two completely different merge semantics. Getting this wrong produces
"my fix didn't apply" and "my fix applied to everyone".

1. **Base** — `unified_model_resource_method.config`.
2. **Environment override** — `environment_unified_model_resource_method.config`,
   `deepmerge(base, override, { arrayMerge: overwrite })`
   (`environmentUnifiedModelResourceMethodService.ts:445-447`).
   - Arrays are **replaced wholesale**, not concatenated.
   - There is **no way to delete a base key** from an override. You can only add or replace.
     To neutralise something, override it with an empty/inert value.
   - An override-only method (no base row) is valid and included (`:349-372`).
3. **Account override** — `integrated_account.unified_model_override[model][resource][method]`
   (`fetchUnifiedApi.ts:626-632`). This one is **not** a config merge: the override
   expression is compiled separately and its **output** is merged over the base mapping's
   output (`mapResponseToUnifiedModel.ts:237-246, 289-306`). A `query_mapping` override
   returning `truto_replace` replaces the query entirely
   (`mapRequestQueryToUnifiedModel.ts:50-52`).

## 8. `before` / `after` steps

`runSteps.ts`. Step types: `request`, `state`, `replace_data`. Each step:
`{ type, name?, run_if?, delay_ms?, config? }`.

- `request` — `config` is `{ resource?, method, type: 'unified'|'proxy', config: {...}, loop_on? }`.
  `config` may itself be a JSONata string that evaluates to that object (`:185-190`).
  The inner `config` object goes through `@truto/replace-placeholders` with
  `{ data, query, id, body, context, step }` (`:225-233`) — that is `{{placeholder}}`
  substitution, **not** JSONata.
- `state` — evaluates `config.expression` and replaces the accumulator (`:294-303`).
- `replace_data` — swaps the accumulator for a previously named step's result (`:310-315`).
- The accumulator starts at the incoming data and threads through every step; named steps
  are also readable as `step.<name>`.
- `run_if` guards a step; a skipped step is recorded, not an error (`:154-173`).
- `?truto_debug=true` surfaces each step's resolved config in the logs (`:138`).

Only add a `before` step when the provider genuinely needs a prior lookup. Every step is
an extra upstream call on every request.

## 9. Dynamic resource / method dispatch

`getResourceOrMethod.ts`. `resource` and `method` each accept three forms:

1. **String** — the proxy resource/method name. Used as-is (`:64-66`).
2. **Array of selectors** — `{ resource|method, query_param?, query_param_value?, body_field?, body_field_value? }`.
   First match wins, tested against `{...rawQuery, ...query}` and `body` (`:71-90`).
   A selector with neither `query_param` nor `body_field` matches unconditionally — it is
   the default branch, so **put it last**.
   No match throws `InternalServerError` (`:90-94`) — a safe failure, before any call.
3. **`{ expression, resources: [...] }` / `{ expression, methods: [...] }`** — JSONata
   returning a name that must be in the allowlist, else it throws (`:31-63`).
   The allowlist is the safety net: it cannot dispatch to an endpoint you did not list.

**Never add an unconditional default branch to a `delete` or `update` mapping to "make it
work".** That is how a request with a missing param silently mutates the wrong resource.
Failing before the upstream call is the correct behaviour.

## 10. What the platform rejects at write time

`src/common/validateMappingJsonata.ts` runs on `POST`/`PATCH` of the mapping tables and on
`integrated_account.unified_model_override`.

- Parses these as JSONata: `response_mapping`, `query_mapping`, `request_body_mapping`,
  `path_mapping`, `error_mapping`, `request_header_mapping`, `response_header_mapping`,
  `is_partial_expression`, `related_resources`, `resource.expression`, `method.expression`,
  and every `run_if` in `before` / `after` / `related_resources` (`:17-33, 73-97`).
- **Skipped:** a bare identifier matching `/^[A-Za-z_][A-Za-z0-9_-]*$/` — because that is
  an alias, not an expression (`:35-48`). A typo'd alias will therefore **not** be caught here.
- **Never compiled:** `base_url_mapping`, `query_schema`, `side_load.*.response_mapping` (`:12-16`).

Local checks before you publish:

```bash
yarn lint:unified-models                       # scripts/lintUnifiedModels.js, over exported YAML
truto jsonata eval --expression '<expr>' --input ctx.json
truto unified test-mapping --mapping-file m.jsonata --input sample.json
truto unified test-mapping --model crm --resource contacts --integration <slug> \
  --method list --input sample.json --show-mapping
```

`truto unified test-mapping` evaluates `response_mapping` **only**, and cannot evaluate the
object/operator mapping form (`cli/src/commands/unified.ts:320-326`). For anything else use
`truto jsonata eval` and supply the bindings from §4 as top-level keys of the context JSON.

## 11. Mapping cache — a change is not live immediately

`src/integrated-account/MappingCache.ts:45-50`. Mapping configs are cached TTL-only, with
**no invalidation on write**: L1 in-memory 300 s + 300 s stale grace, L2 KV 300 s plus an
edge `cacheTtl`, all jittered.

> Worst case a value stays serveable for **roughly 23 minutes** after the write.

So: a live call that still shows old behaviour right after an edit is **not** evidence the
edit failed. Re-read the row to confirm the write landed, then wait or test on a fresh
account. Never "fix" a mapping twice because the first fix appeared not to take.

## 13. Traps that produce silently wrong data

- **`$firstNonEmpty` skips only `null` and `undefined`** — it correctly preserves `false`
  and `0` (`dist/esm/index.js:1650-1656`). It is safe for booleans. What it does *not* do is
  skip `""` or `[]`, so an empty string from the provider wins over a good later fallback.
- **`$mapValues(value, mapping, lowerCase?, default?)` leaks unmapped values.** On no match
  it returns the **original provider value**, not the default — `default` applies only when
  the input is `null`/`undefined` (`dist/esm/index.js:1715-1741`). So an unmapped provider
  status lands verbatim in a unified enum field and silently violates the schema. Enumerate
  every documented provider value, and add an explicit final fallback when the unified enum
  is closed:
  `$exists(m) ? m : "other"` where `m` is the `$mapValues` result checked against the enum.
  Matching is case-insensitive (mapping keys are lowercased), and it recurses into arrays
  and object values.
- **Type coercion only happens in the object mapping form**, driven by the unified schema
  (`mapResponseToUnifiedModel.ts:334-346`). A **string JSONata** mapping does no coercion —
  if the schema says `string` and the provider sends a number, you must `$string(...)` it.
- **Dates.** `format: date-time` needs a real ISO string. Unix seconds →
  `$fromMillis(v * 1000)`; guard the type first (`$type(v) = "number" ? …`), because a
  provider that sometimes sends ISO will produce garbage otherwise.
- **`is_partial_response: true`** declares the record is incomplete. Set it when the method
  cannot populate the schema's core fields (e.g. a list endpoint returning only ids and
  names), or use `is_partial_expression` to decide per record.
- **Empty-body providers.** A `create` returning `204`/only an id needs an `after` hydration
  step or `response_mapping: get`, not a mapping invented from the request body.
- **`update` with PUT semantics** wipes unsent fields. Check whether the provider does
  PUT-replace before mapping only the changed fields.
