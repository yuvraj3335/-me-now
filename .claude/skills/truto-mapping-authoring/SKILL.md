# Authoring a Truto unified mapping

**Load `truto-mapping-reference` first.** It holds the runtime facts — bindings per field,
`mapping_version` semantics, schema vocabulary, the override ladder. This skill is the
*procedure*; that one is the *truth*. Do not author from memory of either.

## The one rule

> **Never write a mapping against config you have not read, or a provider endpoint you have
> not seen documented.**

Every recurring class of bad mapping traces back to skipping that: a proxy resource that
doesn't exist, a `response_path` that doesn't match, a field invented because the unified
schema demanded one. When you cannot get the evidence, say so and stop — see *Blocked*.

---

## Phase 1 — Discover (never skip, never guess)

Work top-down. Each step's output constrains the next.

**1. The unified contract.**
`src/unified-model/models/<domain>.yml` → `resources.<resource>.schema.properties`.
This is the field set you are allowed to emit. Also check `resources.<resource>.methods`
for declared custom methods, and `deprecated`.

**2. The existing mapping for this integration.**
```bash
truto unified-model-mapping list --integration-name <slug> --resource-name <resource>
truto unified-model-mapping get <id>
```
Learn *this integration's* conventions: alias reuse, enum normalisation, date handling,
whether it uses `before` steps. Match them.

**3. Sibling mappings for the same resource, other integrations.**
```bash
truto unified-model-mapping list --resource-name <resource> --method-name <method>
```
Two or three siblings tell you what the repo considers the correct *meaning* of each
unified field. This is how you avoid a semantically-wrong-but-schema-valid mapping.

**4. The proxy transport.**
```bash
truto integration list --name <slug>
truto integration get <id>          # config.resources.<resource>.<method>
```
Confirm `path`, `method`, `response_path`, `pagination`, `body_format`, static `query`
and `headers`, `query_array_format`, `scopes`, `base_url` override.

If the local mirror exists (`src/integration/integrationConfig/<slug>.json`, generated by
`yarn sync:integration` — see reference §1) reading that is faster. If it does not exist,
**it was never generated** — use the CLI, do not assume.

**5. The provider's own docs.** The exact endpoint. Request shape, required fields,
writable-on-update fields, response shape, pagination, delete semantics, empty-body
behaviour. If the user gave doc links, read them.

**6. A real response.** Nothing beats one:
```bash
truto proxy <resource> -a <account-id> -q limit=1
```
Read-only calls only at this stage.

### If the proxy endpoint doesn't exist yet

Say so explicitly, then add it to `integration.config.resources.<resource>.<method>` using
`ResourceMethodSchema` (`src/integration/integrationSchema.ts:403-435`). Model it on a
sibling method in the *same* integration — auth, headers and pagination are usually shared.
Do not duplicate config already set at integration level (`base_url`, `headers`, `query`,
`pagination`, `query_array_format`) into the resource method.

## Phase 2 — Write

Always: `resource`, `method`, `mapping_version: 2`. Canonical key order per reference §2.

### `response_mapping`

- `response.{ ... }` — for **every** method including `list`. See reference §5.
- `response` is already positioned at the proxy method's `response_path`.
- Map only fields in the unified schema. No provider-specific extras — `remote_data` already
  carries the raw record, and the runtime adds it.
- Emit the provider's own record id as `id`. Foreign ids belong in their nested reference
  object (`owner: { "id": … }`), never reused to fill an unrelated required field.
- Coerce explicitly — a string JSONata mapping does no type coercion (reference §13).
- Reuse rather than restate: if `get` returns the same shape as `list`, write
  `response_mapping: list`.
- Every conditional branch must return the **same** unified shape.

### `query_schema` / `query_mapping`

- Prefer field names from the unified **response** schema — a caller filtering on `status`
  should not have to learn the provider's `state_id`.
- A field that is *not* in the response schema is allowed only when it is genuinely needed
  for routing, path construction, or a provider-mandated filter — and its `description`
  must say so.
- `required: true` when the request cannot be safely built without it: path placeholders,
  resource/method dispatch keys, provider-mandated params. Missing-required is caught before
  the upstream call; a silent default is not.
- `query_mapping` emits **only** params the provider documents. Bindings: `query`, `body`,
  `context`, `before`, `id` — no `rawQuery`.
- Decide deliberately what happens when an optional query is absent.

### `request_body_schema` / `request_body_mapping`

- Derive the schema from the unified resource schema. Only fields a caller may legitimately
  send for *this* operation.
- `required: true` only where the provider actually requires it.
- For `update`, only writable fields — and check whether the provider does PUT-replace,
  which would wipe unsent fields.
- Build exactly the documented body. Omit keys with no value unless the provider
  requires an explicit null.
- Do not map an unrelated unified field just to satisfy a provider-required slot. If there
  is no honest source, the field belongs in `request_body_schema` as required input.

### Dispatch, steps, partial responses

- Dynamic `resource`/`method`: array-of-selectors or `{ expression, resources }`. Reference §9.
  The unconditional selector goes **last**, and never on a destructive method.
- `before` only when the provider needs a prior lookup; `after` for hydration when create
  returns an empty body or only an id.
- `is_partial_response: true` when the method structurally cannot fill the schema's core
  fields; `is_partial_expression` when it varies per record.

## Phase 3 — Validate before publishing

```bash
truto unified test-mapping --mapping-file m.jsonata --input sample.json    # response_mapping
truto jsonata eval --expression '<expr>' --input ctx.json                  # anything else
yarn lint:unified-models
```

Test **every branch** of a conditional mapping with a representative sample, including the
empty/missing case. For `truto jsonata eval`, the context JSON's top-level keys are the
bindings — use the exact set for that field from reference §4.

Then, with a real account: `list` first, `get` on an id taken from that list.

**Do not run live `create` / `update` / `delete` without explicit approval in this
conversation.** Approval for one is not approval for the next.

After publishing, remember the mapping cache: up to ~23 minutes of staleness, no
invalidation on write (reference §11). Old behaviour on a live call is not proof your write
failed — re-read the row instead of re-applying the fix.

---

## Output

Return the mapping config (YAML or JSON to match what the user is working in), only the
methods asked for, in the order asked. Name the proxy `resource`/`method` you targeted and
the doc URL you mapped against, so the reviewer can check you without redoing discovery.

Note anything you inferred rather than verified — that list is the review's starting point.

## Blocked

If the config, the docs, or a real response are unavailable or contradictory, do not
produce a plausible mapping. State exactly what is missing:

```
INSUFFICIENT_INPUT: <specific missing or conflicting items>
```

Then say what you *can* do — the reviewed discovery so far, the mapping for the methods that
are fully evidenced, the one call needed to unblock the rest. Partial work with an honest
boundary beats a complete-looking guess.
